**Analysis**:

The failure is a **PE-parsing logic flaw**, not an evasion or detection problem. The loader maps the sacrificial DLL as a `SEC_IMAGE` section and then walks the mapped image to locate the `.text` section header. It bails out with `[-] .text not found or invalid in mapped image` — meaning the section-header walk never matched a section named `.text` (or its size was computed as zero/invalid).

The root cause is a **file-offset vs. RVA confusion combined with the wrong size field**:

1. **Section-header location**: After `NtMapViewOfSection`, the mapped base (`000001C7684C0000`) is the *image base*, not the file base. The section table is reached via `IMAGE_NT_HEADERS` → `FileHeader.SizeOfOptionalHeader` → `SectionTable`, using `e_lfanew` from the DOS header **in the mapped view**. If the code instead used `e_lfanew`/offsets relative to a *file* load or applied `PointerToRawData` as an RVA, the walk lands on garbage and never finds `.text`.

2. **Chosen DLL is a resource-only satellite assembly**: `Microsoft.Activities.Build.resources.dll` (note the `.resources` in the name). Localized resource assemblies frequently contain **only `.rsrc` (and possibly `.reloc`) sections — no executable `.text` section at all**. Even with a perfect parser, there is no `.text` to stomp. This is the most likely direct explanation: the allowlisted auto-pick selected a DLL that has no code section.

3. **Size field**: The comment says Iteration 2 was fixed to use `Misc.VirtualSize` instead of `SizeOfRawData`. That is correct in principle, but if the section is found via a bad pointer the size check still fails. Also `VirtualSize` can be smaller than `SizeOfRawData` for some sections; the write extent must be `min(VirtualSize_or_SizeOfRawData, remaining view)`, and must be clamped to the mapped view (`32768` bytes here) — a 32 KB view is small and easily overrun.

So there are two independent defects: (a) the auto-selection picked a DLL with no `.text`, and (b) the RVA/offset math for locating and sizing `.text` is fragile.

**Technique**: BugFix

**Methodology**:

1. **Guard against resource-only DLLs — validate before stomping.**
   - After mapping, parse the NT headers from the mapped base: `IMAGE_DOS_HEADER->e_lfanew` → `IMAGE_NT_HEADERS64` → `FileHeader.NumberOfSections` → `IMAGE_SECTION_HEADER[]`.
   - Iterate sections and match on the 8-byte name field for `.text` (use `memcmp(sec->Name, ".text", 5)`; do **not** assume null-termination).
   - If no `.text` is found, **fail fast and pick another DLL** rather than aborting. Add a candidate list and iterate until one has a non-empty executable section.

2. **Fix the section-header pointer arithmetic (RVA, not file offset).**
   - Compute headers strictly from the mapped base:
     `dos = (IMAGE_DOS_HEADER*)base;`
     `nt  = (IMAGE_NT_HEADERS64*)((BYTE*)base + dos->e_lfanew);`
     `sec = IMAGE_FIRST_SECTION(nt);`
   - Never add `PointerToRawData` here — that field is meaningless for a mapped image.

3. **Fix the write extent and protection range.**
   - `stomp_size = min(sec->Misc.VirtualSize ? sec->Misc.VirtualSize : sec->SizeOfRawData, payload_size)`.
   - Clamp the destination to the actual mapped view: `dst_end = min(base + view_size, sec_base + stomp_size)`; abort if `payload_size > (dst_end - sec_base)`.
   - `VirtualProtect` exactly `[sec_base, sec_base + stomp_size)` to `PAGE_EXECUTE_READWRITE`, `memcpy` the payload, then restore to `PAGE_EXECUTE_READ` (or leave RWX only for the stomp window).

4. **Choose a stomp source that actually has code.**
   - Replace the auto-pick with a curated allowlist of allowlisted-path DLLs that are known to contain a large `.text` (e.g. a `C:\Program Files\...\*.dll` app DLL, or a `WinSxS\...\*.dll` that is a real code module, not a `.resources` satellite).
   - Explicitly exclude any path containing `.resources` or `NativeImages` resource-only assemblies.

5. **Verify the entry/exec path after stomping.**
   - Compute the payload entry as `sec_base + (payload_entry_offset)`. If using the fiber technique, ensure `ConvertThreadToFiber` succeeded and `CreateFiber(0, sec_base, NULL)` is called with the stomped `.text` address; then `SwitchToFiber`. Confirm the address is inside the mapped view and marked executable before switching.

6. **Add diagnostics** (temporary): print `NumberOfSections`, each section name, `VirtualSize`, `SizeOfRawData`, and the computed `.text` RVA. This will immediately confirm whether the picked DLL is resource-only or whether the parser is misaligned.

**Benign alternative that still produces telemetry**: if the goal is only to exercise the `module_stomping_section_mapping` detection path, map a DLL that *does* have `.text` (e.g. a normal app DLL under `C:\Program Files\`) and stomp it with a **benign payload that writes a marker file or calls `MessageBoxA`** instead of `calc.bin`. That keeps the same NtCreateSection/NtMapViewOfSection + stomp telemetry without requiring a working shellcode stage, and isolates parser correctness from payload correctness.
